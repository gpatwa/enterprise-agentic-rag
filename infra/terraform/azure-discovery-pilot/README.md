# Discovery pilot (Azure Container Apps)

The smallest footprint that serves the Discovery demo: a web Container App (public URL, Entra sign-in required) proxying `/api/` to an API Container App (internal ingress only). Both scale to zero. Plus an Entra app registration for sign-in, a Basic registry, Log Analytics (0.5 GB/day cap), a managed identity with `AcrPull`, and an optional budget alert.

No database, search cluster, model or secret: the API runs on fake providers over a seeded, fictional catalog (`DISCOVERY_ENVIRONMENT=staging`, `DISCOVERY_NO_MODEL=true`). Phase 2 (OpenSearch/PostgreSQL) is deliberately absent. See `docs/DISCOVERY_DEPLOYMENT_PROPOSAL.md`.

**Nothing here is applied by automation.** Applying it is a separate, explicit owner decision. It touches only the new `discovery-pilot-rg` resource group and its own state key.

## Access

Every request to the web app requires an Entra sign-in (Container Apps built-in authentication). The app registration has "assignment required" on, and the **access list** (`access.auto.tfvars`, committed, names only) lists the only accounts assigned to it: anyone else is refused after sign-in. The API has no public ingress.

- Grant or revoke access by a pull request that edits `access.auto.tfvars` (a user principal name and a demo profile such as `user-0001` per person), then apply. Terraform resolves each name to an object ID, assigns the app role, and builds the API's principal map. A name that does not exist fails the plan.
- Get a user principal name with `az ad user show --id <email> --query userPrincipalName -o tsv`. A person outside the tenant must first be invited as a guest (Entra admin center → Users → Invite external user); a guest's name has the `name_domain#EXT#@tenant.onmicrosoft.com` form.
- `allowed_user_object_ids` (object IDs, in the untracked `terraform.tfvars`) still works as an optional extra and is merged with the list; an account already assigned that way keeps its address and is not recreated.
- `allowed_cidrs` is an optional second layer. It is empty by default; `0.0.0.0/0` is rejected.
- The sign-in client secret is created by Terraform, held as a Container App secret and in state, and expires after 180 days; re-apply to rotate it.
- Applying needs rights to create app registrations in the tenant (Application Administrator or Owner of the new app is enough).

## Search VM (OpenSearch, on demand)

Search ranks through OpenSearch on a small VM that is started only for demos. When the VM is off, the API serves the in-memory catalog and responses carry `fallback: true`.

- **Network:** the stack creates a VNet; the Container Apps environment sits in a `/23` subnet (the documented minimum for a consumption-only environment) and the VM in a `/27` subnet with a network security group that allows port 9200 from the environment subnet only and denies everything else inbound. **Putting the environment in the VNet replaces it**, so the first apply recreates both apps and the web URL changes.
- **VM:** `Standard_B2s`, 64 GiB Standard SSD, a static private IP, and an outbound-only public IP (new VNets have no implicit internet access, and the first boot pulls packages and the OpenSearch image). No SSH: port 22 is denied, and a throwaway key (private half in state, never used) satisfies Azure's requirement. Administer with `az vm run-command`.
- **Security:** OpenSearch runs with its security plugin: HTTPS and an `admin` password generated by Terraform. The image's demo certificate is self-signed, so the API sets `DISCOVERY_OPENSEARCH_VERIFY_TLS=false`; this is acceptable only because the port is reachable from one subnet, and the settings reject it in `production`. The password is in state, the VM's custom data and an app secret.
- **Start and stop:** `az vm start -g discovery-pilot-rg -n discovery-pilot-search` / `az vm deallocate ...`, or the manual `discovery-search-vm.yml` workflow (OIDC sign-in with no secret; its five repository variables are set by `make discovery-repo-vars`, see "Zero-manual setup" below). A daily auto-shutdown (`search_shutdown_time`, UTC, default 04:00) is a cost guard; nothing starts it automatically. Allow a few minutes after a start for the JVM.
- **Load or rebuild the index** (after the first start, or if the disk is lost; idempotent):
  ```bash
  az containerapp exec -g discovery-pilot-rg -n discovery-pilot-api --command "python -m app.opensearch.bootstrap"
  ```
  `exec` needs a terminal: from a script or CI-like shell it fails with a `termios` error. Run it from an interactive terminal, or wrap it in `script -q /dev/null ...` and pipe the command to a `sh` session. Verified once: 43 of 43 documents indexed.
- **Subnet delegation:** the `cae` subnet is delegated to `Microsoft.App/environments`; Azure rejects the environment without it.
- **Cost (list prices, not measured):** about 10 USD per month at 40 VM hours (disk 4.80, public IP 3.65, compute about 1.66); about 39 always on.

## Order of operations (when authorized)

1. Create the state backend config from `backend.hcl.example` (a state key of its own).
2. Create the registry first, then push both images, because the apps need an image to start:
   ```bash
   terraform init -backend-config=backend.hcl
   terraform apply -target=azurerm_container_registry.acr -var-file=terraform.tfvars
   ```
3. Build and push `discovery-api` (context: repo root, `services/discovery-api/Dockerfile`) and `discovery-web` (context: `apps/discovery-web`) with the tags set in `terraform.tfvars`.
4. `terraform apply -var-file=terraform.tfvars`, then open `web_url` and sign in with an assigned account.

`.github/workflows/deploy-discovery-pilot-azure.yml` (manual) ships later code changes: it builds both images with the commit SHA, pushes them and updates the two apps. It needs these secrets in the chosen GitHub environment, which the owner sets: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `DISCOVERY_ACR_LOGIN_SERVER`, `DISCOVERY_RESOURCE_GROUP`, `DISCOVERY_API_APP_NAME`, `DISCOVERY_WEB_APP_NAME`. It has never been run.

## Zero-manual setup (design: `docs/ZERO_MANUAL_SETUP_DESIGN.md`, work item A)

Declared here, **planned but not applied** (see `docs/DISCOVERY_STATUS.md`). Always read the plan first: `terraform plan -out=tfplan`, then `terraform apply tfplan`. The first plan against the existing state adds 12 resources, changes 2 in place and destroys none.

| Change | What it adds | Rollback |
|---|---|---|
| **Sign-in app as API** (`resources.tf`) | A `single_page_application` redirect URI (`https://<web fqdn>/`, no wildcard) beside the unchanged easy-auth `web` callback; the delegated scope `access_as_user`; identifier URI `api://<client id>`; `requested_access_token_version = 2`; admin consent for that one scope on this app (so the silent sign-in never shows a consent screen). | Revert the commit and apply. The scope must be disabled before Entra lets it be removed, so a revert applies in two steps: set `enabled = false` on the scope and apply, then delete the block and apply. The easy-auth callback is untouched throughout, so the sign-in gate on the web app is not affected by any step. |
| **Access list** (`access.tf`, `access.auto.tfvars`) | App-role assignments and the principal and tenant maps from user principal names. | Revert the file. Removing a name removes that person's assignment on the next apply. |
| **API auth, off by default** (`enable_api_auth`) | When true: `DISCOVERY_AUTH_ENABLED`, `DISCOVERY_ENTRA_TENANT_ID`, `_AUDIENCE` (the client id), `_REQUIRED_SCOPE`, `_TENANT_MAP` and `_PRINCIPAL_MAP` on the API; the three `VITE_ENTRA_*` values become repository variables. Also always sets `AZURE_CLIENT_ID` on the API so a managed-identity token request names the apps' identity. | Set `enable_api_auth = false` and apply (the API accepts unauthenticated calls again; the next web deploy builds without a token). |
| **GitHub OIDC for the VM workflow** (`github-oidc.tf`) | An app registration and service principal for GitHub (no secret), a federated credential for `repo:<github_repository>:environment:<env>` per entry in `github_environments`, and a custom role that allows read, instance-view, start and deallocate on the search VM only, assigned at the VM. | `terraform destroy -target=azurerm_role_assignment.github_vm_operator -target=azurerm_role_definition.search_vm_operator -target=azuread_application_federated_identity_credential.github_vm -target=azuread_service_principal.github_vm -target=azuread_application.github_vm`. The workflow then fails at sign-in; `az vm start` by the owner still works. |
| **Azure OpenAI** (`openai.tf`, `enable_openai`) | An account (custom subdomain, key authentication disabled), a `text-embedding-3-small` GlobalStandard deployment (capacity 10, thousands of tokens per minute), and `Cognitive Services OpenAI User` for the apps' identity (plus `openai_user_object_ids`). No call is made and the API's embedding stays off. | `enable_openai = false` and apply, or `terraform destroy -target=azurerm_cognitive_deployment.embedding -target=azurerm_cognitive_account.openai`. A deleted account keeps its name for a while; the random suffix avoids a clash on re-create. |

**Order for a full rollout.** (1) `terraform apply` with `enable_api_auth = false`. (2) `make discovery-repo-vars-plan`, then `make discovery-repo-vars` (needs your `az` and `gh` sessions; sets five VM-workflow variables and clears the three web ones). (3) Run `discovery-search-vm.yml` with status and environment `discovery-pilot` to prove the OIDC sign-in. (4) When the web app can sign in (stream B), set `enable_api_auth = true`, apply, run `make discovery-repo-vars`, then run the deploy workflow so the web image is built with the new settings. Between the apply and the deploy the API refuses the old web build; if that matters, deploy the new web image first (it only sends a token when the three settings are present) or set `enable_api_auth` back to false.

**Variables the workflows read** (all repository variables, none secret): `DISCOVERY_AZURE_CLIENT_ID`, `DISCOVERY_AZURE_TENANT_ID`, `DISCOVERY_AZURE_SUBSCRIPTION_ID`, `DISCOVERY_RESOURCE_GROUP`, `DISCOVERY_SEARCH_VM_NAME` (VM workflow); `DISCOVERY_ENTRA_CLIENT_ID`, `DISCOVERY_ENTRA_TENANT_ID`, `DISCOVERY_ENTRA_API_SCOPE` (deploy workflow's web build). They carry a `DISCOVERY_` prefix because the repository already has `AZURE_CLIENT_ID` and friends for other stacks. The deploy workflow's own Azure sign-in and names still use the secrets listed above; giving it a deploy identity is not part of this change.

**GitHub environment.** The federated credential only trusts jobs that run in the environment `discovery-pilot` (a GitHub environment is created the first time a workflow names it). An environment with no protection rules can be used by any branch of the repository, so add required reviewers or a branch restriction in the repository settings if that matters; the credential cannot be used from any other repository.

**Tokens.** The API checks, for a version 2 access token: signature against the tenant's published keys, `iss = https://login.microsoftonline.com/<tenant>/v2.0`, `aud = <client id>` (a GUID, not `api://...`), `tid`, `oid`, and `scp` containing `access_as_user`. The scope check keeps an ID token for the same app (same audience, no scope) from working as an API token. A version 1 token (`aud = api://<id>`, `iss = sts.windows.net`) is refused, so a missing `requested_access_token_version` fails closed.

**Embeddings by managed identity.** `DISCOVERY_AZURE_OPENAI_AUTH=key|managed_identity|az_cli` (default `key`). With `managed_identity` or `az_cli` no key is configured, the token is requested for `https://cognitiveservices.azure.com/.default`, and a 401 or 403 reports that the identity needs the `Cognitive Services OpenAI User` role (a new assignment can take several minutes to apply). From a laptop: `DISCOVERY_AZURE_OPENAI_AUTH=az_cli`, with your object ID in `openai_user_object_ids`.

## Not verified

- Applied once against the real subscription (2026-11-02): the first apply failed on the missing subnet delegation and the fix was applied. Sign-in at the new web URL was not checked by the tool that applied it.
- The search VM: VM boot time, whether the static public IP bills while the VM is deallocated, and the fallback behavior with the VM deallocated have not been measured. Cloud-init, OpenSearch's first start, the bootstrap, and API-to-VM connectivity were exercised once.
- The Easy Auth redirect (`/.auth/login/aad/callback`) and the guest-account sign-in flow have not been tested.
- The web-to-API proxy over internal ingress (Host header, plain HTTP) is reasoned from Container Apps routing rules, not tested.
- Cost is not measured. The budget alert is set to the owner's chosen 25 USD.
- The zero-manual-setup changes are `terraform validate`d and planned, not applied. Not verified against a real tenant: a version 2 token for the new app (the tenant's published issuer and key endpoint were checked and match the verifier), the SPA redirect with MSAL (the registered URI has a trailing slash; the web app must send exactly that), the admin-consent grant (needs a role that may grant consent, and the new scope can take a moment to appear so the first apply may need a re-run), GitHub OIDC sign-in with a role that exists only on the VM (that `azure/login` and `az vm` need nothing more), regional quota for the GlobalStandard embedding deployment, and the 401/403 behaviour of a real Azure OpenAI account.
