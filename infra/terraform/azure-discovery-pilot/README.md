# Discovery pilot (Azure Container Apps)

The smallest footprint that serves the Discovery demo: a web Container App (public URL, Entra sign-in required) proxying `/api/` to an API Container App (internal ingress only). Both scale to zero. Plus an Entra app registration for sign-in, a Basic registry, Log Analytics (0.5 GB/day cap), a managed identity with `AcrPull`, and an optional budget alert.

No database, search cluster, model or secret: the API runs on fake providers over a seeded, fictional catalog (`DISCOVERY_ENVIRONMENT=staging`, `DISCOVERY_NO_MODEL=true`). Phase 2 (OpenSearch/PostgreSQL) is deliberately absent. See `docs/DISCOVERY_DEPLOYMENT_PROPOSAL.md`.

**Nothing here is applied by automation.** Applying it is a separate, explicit owner decision. It touches only the new `discovery-pilot-rg` resource group and its own state key.

## Access

Every request to the web app requires an Entra sign-in (Container Apps built-in authentication). The app registration has "assignment required" on, and `allowed_user_object_ids` lists the only accounts assigned to it: anyone else is refused after sign-in. The API has no public ingress.

- Get an object ID with `az ad user show --id <email-or-upn> --query id -o tsv`. A person outside the tenant must first be invited as a guest (Entra admin center → Users → Invite external user); use the object ID of that guest account.
- Revoke someone by removing their ID and re-applying (or by removing the assignment in the Entra portal).
- `allowed_cidrs` is an optional second layer. It is empty by default; `0.0.0.0/0` is rejected.
- The sign-in client secret is created by Terraform, held as a Container App secret and in state, and expires after 180 days; re-apply to rotate it.
- Applying needs rights to create app registrations in the tenant (Application Administrator or Owner of the new app is enough).

## Search VM (OpenSearch, on demand)

Search ranks through OpenSearch on a small VM that is started only for demos. When the VM is off, the API serves the in-memory catalog and responses carry `fallback: true`.

- **Network:** the stack creates a VNet; the Container Apps environment sits in a `/23` subnet (the documented minimum for a consumption-only environment) and the VM in a `/27` subnet with a network security group that allows port 9200 from the environment subnet only and denies everything else inbound. **Putting the environment in the VNet replaces it**, so the first apply recreates both apps and the web URL changes.
- **VM:** `Standard_B2s`, 64 GiB Standard SSD, a static private IP, and an outbound-only public IP (new VNets have no implicit internet access, and the first boot pulls packages and the OpenSearch image). No SSH: port 22 is denied, and a throwaway key (private half in state, never used) satisfies Azure's requirement. Administer with `az vm run-command`.
- **Security:** OpenSearch runs with its security plugin: HTTPS and an `admin` password generated by Terraform. The image's demo certificate is self-signed, so the API sets `DISCOVERY_OPENSEARCH_VERIFY_TLS=false`; this is acceptable only because the port is reachable from one subnet, and the settings reject it in `production`. The password is in state, the VM's custom data and an app secret.
- **Start and stop:** `az vm start -g discovery-pilot-rg -n discovery-pilot-search` / `az vm deallocate ...`, or the manual `discovery-search-vm.yml` workflow (secrets: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `DISCOVERY_RESOURCE_GROUP`, `DISCOVERY_SEARCH_VM_NAME`, set by the owner). A daily auto-shutdown (`search_shutdown_time`, UTC, default 04:00) is a cost guard; nothing starts it automatically. Allow a few minutes after a start for the JVM.
- **Load or rebuild the index** (after the first start, or if the disk is lost; idempotent):
  ```bash
  az containerapp exec -g discovery-pilot-rg -n discovery-pilot-api --command "python -m app.opensearch.bootstrap"
  ```
  `exec` needs a terminal: from a script or CI-like shell it fails with a `termios` error. Run it from an interactive terminal, or wrap it in `script -q /dev/null ...` and pipe the command to a `sh` session. Verified once: 43 of 43 documents indexed.
- **Subnet delegation:** the `cae` subnet is delegated to `Microsoft.App/environments`; Azure rejects the environment without it.
- **Cost (list prices, not measured):** about 10 USD per month at 40 VM hours (disk 4.80, public IP 3.65, compute about 1.66); about 39 always on.

## Order of operations (when authorized)

1. Create the state backend config from `backend.hcl.example` (a state key of its own).
2. Create the registry first, then push both images, because the apps need an image to start:
   ```bash
   terraform init -backend-config=backend.hcl
   terraform apply -target=azurerm_container_registry.acr -var-file=terraform.tfvars
   ```
3. Build and push `discovery-api` (context: repo root, `services/discovery-api/Dockerfile`) and `discovery-web` (context: `apps/discovery-web`) with the tags set in `terraform.tfvars`.
4. `terraform apply -var-file=terraform.tfvars`, then open `web_url` and sign in with an assigned account.

`.github/workflows/deploy-discovery-pilot-azure.yml` (manual) ships later code changes: it builds both images with the commit SHA, pushes them and updates the two apps. It needs these secrets in the chosen GitHub environment, which the owner sets: `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `DISCOVERY_ACR_LOGIN_SERVER`, `DISCOVERY_RESOURCE_GROUP`, `DISCOVERY_API_APP_NAME`, `DISCOVERY_WEB_APP_NAME`. It has never been run.

## Local check (no Azure)

```bash
terraform init -backend=false && terraform validate && terraform fmt -check -recursive
```

CI runs the same three commands.

## Not verified

- Applied once against the real subscription (2026-11-02): the first apply failed on the missing subnet delegation and the fix was applied. Sign-in at the new web URL was not checked by the tool that applied it.
- The search VM: VM boot time, whether the static public IP bills while the VM is deallocated, and the fallback behavior with the VM deallocated have not been measured. Cloud-init, OpenSearch's first start, the bootstrap, and API-to-VM connectivity were exercised once.
- The Easy Auth redirect (`/.auth/login/aad/callback`) and the guest-account sign-in flow have not been tested.
- The web-to-API proxy over internal ingress (Host header, plain HTTP) is reasoned from Container Apps routing rules, not tested.
- Cost is not measured. The budget alert is set to the owner's chosen 25 USD.
