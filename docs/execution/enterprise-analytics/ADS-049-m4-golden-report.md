Status: **Review** (implemented and locally verified; independent review pending)
Milestone: M4
Depends on: ADS-040 to ADS-048

**Threshold approval (recorded 2026-10-08):** the thresholds below were drafted by the implementing
agent from section 10 of the execution plan, and the user then wrote "I approve the proposed
thresholds". The approval is recorded in `m4-thresholds.json` and under `M4.m4_threshold_approval`
in the manifest. It covers only these local M4 reference-stack thresholds. It is **not** the M4

corpus digest needs a new explicit approval with a reviewed rationale.

## Deliverable

- `services/analytics-api/reference_stack/golden/golden-suite-v1.json`: a pinned 14-case corpus
  (6 answers, 3 of them P0; 4 unsupported/unsafe requests including raw-SQL output and prompt
  injection; policy denial; cross-tenant access; ambiguous reference; over-threshold cost).
  Expected rows were computed independently in plain Python from the seed formula (a test
  recomputes them), not by running the system.
- `.../golden/m4-thresholds.json`: the gates, each with the plan gate it comes
  from and how it is measured, the recorded `approval` block, the corpus SHA-256 it was
  drafted against (changing the corpus without updating the digest fails the run), and the plan
  gates that cannot be measured at M4 and why.
- `reference_stack/golden.py`: runs every case on DuckDB and the PostgreSQL emulation (28
  executions), measures all 12 gates, and renders the report. Answer cases run five times for
  latency; each answered run is sealed into the evidence chain and replayed with its idempotency
  key; every executed SQL statement is checked against what the deterministic compiler produced.
- `make analytics-golden` writes `reports/ADS-049-m4-golden-report.md` and `.json`.

## CI finding (PR #15)

On the CI runner DuckDB returned the month bucket as `2024-03-01T00:00:00`, while the local
DuckDB (1.4.4; the requirement is `>=1.1,<2`) returns `2024-03-01`. The value is the same, so
result equivalence now treats a midnight timestamp and its date as equal (`canonical_rows`; any other
difference, including a non-midnight time, still fails). Expected results, the corpus digest, and
the approved thresholds are unchanged. The API itself still returns whatever the engine
produces, so the month-bucket representation is DuckDB-version dependent.

## Boundary

- This is a regression and pipeline-integrity suite, not an accuracy benchmark. The model is
  scripted, the data is 100 rows, PostgreSQL is emulated, and there is no live index or warehouse.
  Meeting these thresholds says nothing about performance with a real model or real data.
- Latency and overhead percentiles come from 60 samples on fast local data; they cannot
  demonstrate a latency gate and must be re-baselined (plan section 10).
- "Raw model SQL" is detected by comparing executed SQL with compiler output; it cannot catch a
  compiler bug that emits unsafe SQL (the AST validator and gateways are separate defenses).
- Tenant isolation is tested at the API for one foreign tenant and one run-ID probe.
- ADS-070/071 own the 100-case corpus and the full correctness evaluation; this suite is not
  a substitute.
