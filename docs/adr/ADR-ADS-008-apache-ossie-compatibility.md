# ADR-ADS-008: Apache Ossie Compatibility Boundary

Status: Proposed for independent review
Date: 2026-09-05
Owners: Architecture and semantic platform
Depends on: [ADR-ADS-001](ADR-ADS-001-agentic-data-stack-boundary.md)

## Context

Compass Analytics has a versioned internal semantic contract in
`packages/platform_contracts/semantic.py`. It models tenant scope, stable IDs,
owners, datasets, fields, entities and grain, dimensions, metrics, approved
joins, filters, policies, lifecycle, and cross-reference validation. The
contract is the authority used by the future registry, typed intent validator,
compiler, policy gate, evidence record, and execution adapters.

Apache Ossie provides an open interchange format for semantic models. The
current upstream core specification examined for this decision is
`0.2.0.dev0`, a draft whose schema may change before `0.2.0`. Its core model
contains semantic models, datasets, fields, relationships, metrics, dialect
expressions, AI context, and custom extensions. It does not provide all of the
trust and operational controls required by the Compass runtime.

This decision therefore defines interoperability at an explicit boundary. It
does not make Ossie the Compass runtime contract, and it does not make a model
generated by an LLM or imported from Ossie eligible for execution by itself.

## Decision

Compass will implement a version-pinned Apache Ossie import/export boundary in
`ADS-011`, using the mapping in
[ADS-008 Ossie to Compass mapping](ADS-008-ossie-compass-mapping.md).

The boundary has four rules:

1. The Compass semantic contract remains authoritative for certified analytics.
2. Only fields with an equivalent, validated Compass representation may enter
   the certified lifecycle through import.
3. Compass-only metadata is preserved in namespaced extensions where safe, but
   extensions never grant execution authority and are never interpreted as
   policy without a separate deterministic validator.
4. Every import and export emits a compatibility report with source version,
   mapping version, preserved extensions, lossy fields, rejected fields, and
   round-trip status.

The initial support level is deliberately narrow: datasets, simple physical
fields, primary-key grain, many-to-one relationships, time dimensions, and
simple single-dataset aggregate metrics can round-trip. Computed expressions,
cross-dataset metric formulas, reusable filters, ontology objects, row-level
policies, and operational evidence do not silently enter the certified path.

## Authority and trust boundary

| Concern | Authority | Ossie relationship |
|---|---|---|
| Physical rows and source permissions | Customer database or approved file source | Not represented by Ossie; never inferred from an Ossie document |
| Business meaning used for execution | Certified Compass semantic contract | Ossie can provide a draft input or portable subset |
| Tenant, principal, purpose, and ACL | Compass identity and deterministic policy gates | Compass extension or request context; never Ossie AI context |
| Lifecycle and certification | Git-backed Compass registry and review | Compass extension; absent on import means `draft` |
| Provenance and source versions | Compass context/provenance contracts | Compass extension; required for certification |
| SQL compilation and dialect safety | Compass typed intent and deterministic compiler | Ossie expressions are source data, not executable planner output |
| AI instructions and synonyms | Compass context policy after sanitization | Ossie `ai_context` is untrusted context and may be preserved |
| Query evidence and audit | Compass evidence store | Not core Ossie data; export only as explicitly approved extension |

An imported document with no tenant or provenance metadata may be parsed for
inspection, but it cannot be certified, retrieved into a certified context
pack, compiled, or executed. An exported document never grants access to the
underlying data.

## Versioning

Three version identifiers are kept separate:

- `ossie_spec_version`: the upstream format version, initially
  `0.2.0.dev0`.
- `mapping_version`: the Compass mapping rules, initially `ads-008.v1`.
- `contract_version`: the Compass semantic contract schema/version, initially
  `v1` plus the contract's own business version.

The importer must reject an unknown Ossie major version and must not silently
reinterpret a changed draft schema. A known minor or development version may
be accepted only when its schema fingerprint is pinned in the compatibility
implementation. The exporter emits the pinned Ossie version and a Compass
extension containing the mapping and contract versions.

Changing a classification from supported to supported, or changing any
conversion rule, requires a new mapping version and compatibility fixtures.
Lossy-to-supported changes require independent semantic review. Contract
version changes remain governed by the Compass registry lifecycle.

## Import behavior

1. Validate the input against the pinned Ossie JSON Schema before conversion.
2. Record the source bytes or content fingerprint, source URI/reference, Ossie
   version, tenant supplied by the import request, and importer version.
3. Convert only the supported subset into a Compass draft contract.
4. Preserve recognized Compass extensions without executing or trusting them.
5. Emit warnings for lossy fields and errors for unsupported fields that are
   required to define an unambiguous metric, relationship, or field.
6. Run Compass cross-reference and tenant/provenance validation.
7. Keep the result `draft` until an owner reviews the compatibility report and
   certifies the contract through the normal registry workflow.

The importer must not invent tenant policy, owner approval, physical data
permissions, freshness, quality, or certification from names, descriptions,
`ai_context`, or custom extensions. It must not import a raw metric expression
as executable SQL into the typed intent or compiler.

## Export behavior

1. Export only a selected Compass contract version and an explicit target
   Ossie version.
2. Emit the portable subset using Ossie core names and structures.
3. Preserve stable Compass IDs, provenance references, lifecycle, tenant, and
   policy references in a namespaced `custom_extensions` entry when the
   recipient has opted into Compass extensions.
4. Without the extension, report which Compass controls are omitted; do not
   claim a fully faithful export.
5. Do not export customer rows, credentials, access tokens, raw audit payloads,
   or private policy predicates by default.

An export is a semantic model artifact, not a permission grant and not a query
execution plan.

## Round-trip contract

Round-trip success means `import(export(contract))` preserves the selected
portable semantic subset after canonicalization, including stable IDs,
dataset/field references, primary-key grain, relationship key order,
time-dimension markers, and simple metric meaning. It does not mean that all
Compass metadata fits in Ossie core.

The compatibility report must distinguish:

- `round_trip: exact_subset`: all exported portable fields re-import without
  semantic change.
- `round_trip: extension_preserved`: Compass-only metadata survives through a
  recognized Compass extension.
- `round_trip: lossy`: an explicitly listed field or distinction is not
  reconstructable; the result is not eligible for certified execution.
- `round_trip: rejected`: the source cannot be represented safely.

ADS-011 owns executable import/export and round-trip fixtures. ADS-008 fixes
the classification and the report contract; it does not implement a converter.

## Alternatives considered

| Alternative | Decision | Reason |
|---|---|---|
| Make Ossie the internal Compass contract | Rejected | Ossie draft evolution does not cover Compass tenant, policy, lifecycle, provenance, and evidence requirements. |
| Ignore Ossie until it is stable | Rejected | The interchange boundary is low-cost now and avoids coupling future imports to runtime internals. |
| Preserve every unsupported field as executable metadata | Rejected | Opaque preservation is useful for portability, but it cannot bypass validation or trust controls. |
| Build a full bidirectional converter in ADS-008 | Rejected | The ADR must settle authority and loss rules before implementation; the converter belongs in ADS-011. |

## Consequences

Positive consequences:

- Compass can exchange a useful portable semantic subset without surrendering
  its trust model.
- Future Ossie schema changes are isolated behind a versioned mapping.
- Compatibility failures become reviewable evidence instead of silent drift.
- The same semantic contract can support PostgreSQL and DuckDB without using
  Ossie dialect expressions as raw planner input.

Costs and risks:

- Some Ossie models will import only as drafts or be rejected.
- A Compass extension namespace must be documented and maintained.
- Draft Ossie semantics around grains, filters, and derived metrics may require
  mapping revisions as the community specification evolves.
- Round-trip fidelity is a subset property, not a promise of lossless
  conversion for the whole Compass contract.

## Review questions

1. Is the supported subset narrow enough to protect compiler and policy
   boundaries?
2. Are loss and rejection rules explicit enough for a customer-facing report?
3. Is the separation between Ossie `ai_context` and Compass authorization
   clear?
4. Are the versioning and draft-spec stop conditions sufficient?
5. Does the mapping preserve enough stable identity for future registry use?
